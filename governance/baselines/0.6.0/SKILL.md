# 代码方案多审（codeplan-multireview）

## 身份

开发需求时描述一个问题。扫过代码仓后发现要改代码或有 bug，就问要不要出一版升级方案。同意后由 Agent A 按固定十节写方案，不必先指定审核人数。每名 Agent B 使用人点名的别名，或自加「B-」加八位十六进制别名，只在自己的大章节下追加。B 先按自己读到的代码和方案里的问题独立推导并提问，再看方案做法和辩驳。Agent A 对应该 B 的每一问做出解释，且该 B 认可之后，该 B 才能写可以执行。人没有明确要求时，Agent A 不得主动拉起子代理担任审核。人要求派出时可以派。审核用哪一个模型，只由人决定。已经出现的每一名 B，其最后一轮都是可以执行且对照修订等于当前 revision 时，人说出「开始按方案执行」，才由 A 按方案改代码。还没有全部准许时，这一次不改代码；人另起一条消息再次说出「开始按方案执行」，才可以直接执行。触发：出一版升级方案、你是 Agent A、你是 Agent B、审核这份方案、开始按方案执行。

硬闸在下面。步骤在 `references/01-plan-review.md`。

## 工作区

打开本 Skill 所服务的工作目录。业务方案写在该目录的 `outputs/codeplan/`，不写进技能开发仓的 `governance/planning/`。步骤见 `references/01-plan-review.md`。

## 硬闸

1. 扫过所服务的代码仓，发现要改代码或有 bug：先问要不要出方案。人同意前不写方案、不改代码。
2. 审核人数不在写方案之前询问，也不用来选择十节模板。不得自行定成 2，也不得自行定成任何人数。人同意出方案之后就写方案正文。不要先问审核人数，也不要按人数预建 B 文件。文首 `reviewers` 先写空名单。人已经点名的别名写入该名单。只改这份名单不算新修订。文首 reviewers 为空，也不等于没有审核。已有 B 章节或 `B*.md` 时，按那些别名审核，不回头问人数。人没有在当条消息里明确要求派出子代理时，不得主动拉起。人在当条消息里明确要求派出子代理时，可以派出。明确要求是这句消息里同时有「派」或「开」，以及「子代理」或「子助手」。同意出方案、设置审核人数、点名别名、说「审核」、方案写完或修订完成，都不是明确要求。一次明确要求只授权这一次。审核用哪一个模型，只由人决定。人没点名模型时，用当前对话的模型，不自行改换。未经当条消息明确要求而拉起的子代理，其轮次不算准许。
3. 方案正文只由 Agent A 写。Agent B 不改方案正文，不写代码。写过方案正文的这场对话不担任任一 B。
4. 每个 Agent B 只追加自己的大章节。标准目录里，章节就是该别名的 `B*.md`，只在该文件末尾追加。人指定单个方案文件时，章节是围栏之外的一行 `# Agent {别名}`，新的一轮只插在该标题之下、下一个 `# Agent ` 标题之前。没有该标题时，才在文件末尾新开这一章。不得把一轮写进其他别名的章节。不看其他 B 的审核结果。每一轮自己重读磁盘上的最新代码；方案里的代码摘录、上一轮记录、别的助手的转述，都不能当审核依据。
5. 决定能不能改代码之前，必须读完格式样例之后的每一节「## 第N轮」。较早一轮的对照修订不等于当前 revision，不因此停读。文件里已有 `# Agent ` 章节时，每一章只看该章最后一节真实轮次。文件里还没有 `# Agent ` 章节时，人给出一个方案文件，只看该文件最后一节真实轮次。人走标准目录、没有另外指定单个文件时，该目录下每一个 `B*.md` 的最后一节真实轮次都要看。`a-body.md` 和 `plan.md` 不算。已出现的每一名 B 都准许执行时，人说出「开始按方案执行」后，才由 Agent A 按方案正文改代码。还没有全部准许时，这一次不改代码。人另起一条消息再次说出「开始按方案执行」，才可以直接执行。第二条确认去掉首尾空格后，正文只能是这八个字：开始按方案执行。不含标点，不含引号。最后一节真实轮次已经在指定文件里时，人不必再指出，也不必把该轮贴进对话。拍板前点名的代码有新改动时，不改代码。格式样例里的「可以执行」不算一轮。还没有 B，也没有旧稿里的真实轮次时，第一次口令不改代码。结论是「不可执行」时，不改代码。交给审核骨架里没有「### 覆盖」的已有一轮，不因缺少安全评估、反问或覆盖而无效。不能执行时，回复写明最后一节的标题、对照修订和结论，不得把较早一节说成文件末尾。
6. 未确认的破坏性改动先问。
7. 不要把 `governance/` 写进分发包。
8. 每一名 Agent B 的每一轮，都要对照当前方案和本轮从磁盘读到的代码，把这一轮已经能发现的问题一次写进「发现」。不要把当时已经能看到的问题拆开，留到后面几轮再提。Agent A 改了方案，或方案点名的代码在两轮之间变了，下一轮可以提出由此新出现的问题。
9. 标准方案只由安装了本技能的 Agent A 写出。文首 YAML 之后固定十节：问题、代码仓、修改空间、现状、处理、执行、不改什么、验收、自审、交给审核。人指定单个 Markdown 时形状相同。自审有一项不是「通过」，就不交给 B。
10. 代码仓是允许阅读的根路径。修改空间是允许修改的文件，每一项必须落在代码仓内。执行不得超出修改空间。佐证点名的路径必须落在代码仓内。
11. Agent B 不要求安装本技能。方案「交给审核」一节是 B 的全部工作说明。B 阅读代码仓里的佐证，核对修改空间里的改动。追加只能是自己章节里的 `## 第N轮`。提问轮的 `### 结论` 下一行只能是 `不可执行`。认可轮的 `### 结论` 下一行只能是 `可以执行` 或 `不可执行`。不要写总体评价，不要用 A/B/C/D 分节。修改空间之外的文件不得写成要改的对象。提示词里没有「人已明确要求派出子代理」，且这场也不是人自己另开的对话时，第一句写「子代理不能审核」，不要写轮次。
12. 自己的章节里没有本轮的「## 第N轮」时，回复第一句是「没有写入」加该路径。自己的章后面还有别人的章时，本轮不在整份文件末尾也算写入成功。禁止用对话长文冒充已经追加。两处都写不进去时，第一句仍是「没有写入」，然后只放一次围栏，围栏上一行写「未落盘」。
13. 方案「验收」必须有「回归验证」和「bug修复验证」。回归验证写升级改造的本次结果，并写可能受影响的关联业务以及怎么确认它仍正常运转、逻辑没有改变。报错或 bug 归 bug修复验证，写清问题链路怎样算已经修复；没有这类问题时写「无」。执行里每一行要落地的代码，上一行一条中文注释，只说明这一行的用处，简洁直译。按方案改完代码后，按验收逐条验证再结束。
14. 现状里的链路，每一行已有注释都要核对。改完后代码和注释对不上，或原注释看不出这一行在做什么，注释的修改和补充写进执行，算代码改造。链路以外的行不加注释，也不改它们已有的注释。硬闸 13 的注释要求适用于执行里每一行要落地的代码，包括链路以内改写或补上的注释。链路以外不改的行不受硬闸 13 约束。逻辑有变化时，执行里补上日志，不写口令、密钥、令牌、完整报文。完整报文指包含请求或响应全部字段的原始文本。不含凭证、且已经脱敏的业务字段可以写入日志。自审必须写出安全评估：这么改行不行、符不符合安全。评估结论不是通过，就不交给 B。现状没有把链路写到函数或语句块时，自审不通过，不交给 B。
15. 下面关于安全评估、反问和覆盖的不算一轮，只用于交给审核骨架里已经写有「### 覆盖」之后新追加的一轮。骨架里没有「### 覆盖」的已有一轮，不因缺少安全评估、反问或覆盖而无效。交给审核骨架里没有「### 独立推导」的已有一轮，不因缺少独立推导、提问或认可而无效。提问轮只有独立推导、提问和结论，不因缺少安全评估、反问或覆盖而无效。认可轮仍要有安全评估、反问和覆盖。Agent B 在认可轮自己做安全评估，写在本轮「安全评估」里，不照抄方案「自审」里的安全评估。回答这么改行不行、符不符合安全。只写「通过」不算填实。结论不是通过，这一轮就是不可执行。认可轮对每个问题反问：为什么这么写，有没有问题，有没有更好的实现方式。反问的任一子项写了「无」，不算一轮。回答要指到本轮读到的代码。认可轮在「发现」之前写一节，标题是 `### 覆盖`，五格为链路、注释、日志、安全、更好实现。五格有一格空着不算一轮。只写「没有」不算填实。只写「已看」不算填实。只写「通过」不算填实。覆盖里写了问题，发现必须逐条列出，漏一条不算一轮。有问题，或存在更安全、改动更少却仍满足该问题、或能避开方案缺陷的做法，写入「发现」，结论写不可执行。只是另一种写法、结果相同、安全性相同，不因此不可执行。A 改了方案之后，下一轮五格重新填，并只加写新出现的问题。反问不是总体评价，也不用 A/B/C/D 分节。A 这一次修订要处理该轮发现里的全部问题，不要只改其中一条。
