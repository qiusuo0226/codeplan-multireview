## Acceptance Criteria

1. 人已经同意出方案、还没有方案文件、也没有说出审核人数时，Agent A 写出固定十节正文，`reviewers` 为空名单，不先问人数，不按人数预建 B 文件，不把人数定成 2 或任何其他人数，不改业务代码。
2. 人点了别名时，该 Agent B 只用这个别名。人没点名时，该 B 自加「B-」加 8 位小写十六进制，不用文件里已有的别名，也不自取 B1、B2 这种序号。
3. 每个别名只有自己的大章节。标准目录里是该别名的 `B*.md`，只在该文件末尾追加。人指定单个文件时，章节是围栏之外的 `# Agent {别名}`，新的一轮只写在该标题之下、下一个 `# Agent ` 标题之前。不得写入其他别名的章节。
4. 交给审核骨架里写有「### 独立推导」时，提问轮只根据本轮读到的代码和方案「问题」写独立推导和提问，结论是不可执行。Agent A 在「处理」下用自己的话逐条解释。认可轮才对照方案做法和辩驳。该章上一提问轮的每一问都写了认可，辩驳没有剩余实质分歧，并且原有的安全评估、反问、覆盖条件都满足，结论才能是可以执行。
5. 已经出现的每一名 B，其章节内最后一轮都是可以执行，且对照修订等于当前 revision 时，人说出一次「开始按方案执行」，Agent A 才按方案改代码。还没有 B，或有任一名的最后一轮不是这样时，这一次不改代码。人另起一条消息，正文只有「开始按方案执行」，才可以直接执行。
6. 交给审核骨架里没有「### 独立推导」的已有一轮，不因缺少独立推导、提问或认可而无效。五句触发短语不变。十节名称和顺序不变。`references/gap-capture.md` 与 `governance/baselines/0.1.0/references/gap-capture.md` 逐字节相同。
7. 人在当条消息里明确要求派出子代理时，Agent A 可以派出。写完方案、修订完、设置审核人数或只说「审核」，都不是这种要求，A 不得主动拉起。人没点名模型时用当前对话的模型，不自行改换。提示词里没有「人已明确要求派出子代理」的子代理，第一句写「子代理不能审核」，不写轮次；这种轮次不算准许。
8. `governance/rules/upgrade-dual-agent.md` 第 4 节第 3 步写明：用编辑工具把审核节写入 AP 文件末尾，不得只输出在对话回复里，追加后回读，写入失败时回复第一句是「未写入」加路径。`governance/templates/upgrade-plan.md` 末尾改成可见文字，含同样的要求。效果核对九节不改。人说一次「同意执行」或「执行升级」仍是改技能的口令。
