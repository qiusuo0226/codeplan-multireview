# 多审步骤

带编号的「你是 Agent B{n}」与「你是 Agent B」「审核这份方案」走同一套 B 步骤。「出一版升级方案」「你是 Agent A」「写方案」走 A 的步骤。「开始按方案执行」走写代码一节。

硬闸以 `SKILL.md` 为准。本文件只写做法，不另抄一套禁令。派 B 的提示词全文只在第 9 节。

## 1. 何时出方案

见硬闸 1。扫描后没有发现必须改的代码或 bug：告诉人，不出方案，不建目录。

## 2. 角色

| 角色 | 做 | 不做 |
|---|---|---|
| 人 | 同意后才许写方案。可以点名别名。已出现的每一名 B 都准许时，说出「开始按方案执行」才许改代码。还没有全部准许时，这一次不改代码。人另起一条消息再次说出「开始按方案执行」，才可以直接执行 | 不起草 B 的结论 |
| Agent A | 必须安装本技能。写标准方案。各 B 的稿在指定文件上时，把原稿原样拼进 `plan.md`。人指出的一轮不在指定文件上时，不生成缺少该轮的 `plan.md`。按硬闸改代码。人没有在当条消息里明确要求派出子代理时，不得主动拉起。人在当条消息里明确要求派出子代理时，可以派出 | 不起草 B 的结论。不在方案正文第 1 到第 9 节写入 B 的原话、复述或「某 B 认为」。不代替 B 写认可。写出方案正文的这场对话不再担任任一 B |
| Agent B | 不要求安装本技能。先定别名。按方案「交给审核」阅读代码仓里的佐证和修改空间里的文件。标准目录里只在自己的 `{别名}.md` 末尾追加。人指定单个方案文件时，只在围栏之外自己的 `# Agent {别名}` 章内追加 | 不改方案正文、不改 `plan.md`、不改其他 B 的章节、不改已有轮次、不写代码、不看其他 B 的审核 |

人同意出方案之后就写方案正文。不要先问审核人数，也不要按人数预建 B 文件。不得自行定成 2，也不得自行定成任何人数。文首 reviewers 为空，也不等于没有审核。

别名按这个顺序：

1. 人点了名字，例如「你是 Agent B1」或「你是 Agent B-a3f19c02」。别名是点名里 Agent 后面的那一段，去掉首尾空格。
2. 人只说「你是 Agent B」或「审核这份方案」时，先读围栏之外已经有的 `# Agent ` 标题，以及标准目录里已有的 `B*.md`。本场没有写过其中任何一个，就不占用它们。
3. 仍然没有别名时，自加 `B-` 加 8 位小写十六进制。写之前确认指定文件和标准目录里都还没有这个别名。不自取 B1、B2、B3。
4. 别名不得含空格、`#`、`/`、`\`，也不得含 Windows 文件名拒绝的字符。人点的名字里有这些字符时，改用第 3 步，并在自己的章节开头写明人点过的原文。

A 可以在全体已出现的 B 落盘之后阅读那些稿，用来决定要不要改方案。这是汇总。B 之间不读彼此的稿，也不读合订本。

人中途再点一名 B：用该别名。该 B 必须对当前 revision 写出「可以执行」才算数。不因此抬高 revision，已通过的 B 不必重审。人中途让某 B 退出：从 `reviewers` 名单去掉，原稿保留，该 B 不再挡住执行。

## 3. 目录与文件

目录在所服务工作区，人同意出方案之后才懒建：`outputs/codeplan/CP-YYYYMMDD-NNN/`。`NNN` 为当天已有最大号加 1，没有则为 `001`。不要把这份方案写进技能开发仓的 `governance/planning/`。

| 文件 | 谁可写 | 谁可读写 |
|---|---|---|
| `a-body.md` | 只 A | B 可读。这是方案正文，也是执行依据 |
| `{别名}.md` | 只对应的 B，且只能在该文件末尾追加 | 该 B 与 A 可读。其他 B 不可读。自加的别名以 `B-` 开头，文件名因此匹配 `B*.md` |
| `plan.md` | 只 A，整文件覆盖生成 | 人读。每个 B 都不打开 |

`plan.md` 是合订本。每个已有 `{别名}.md` 前面加一行 `# Agent {别名}`。它不是第二份原稿。拼接时不改任何一个字、不加评语：

```
# 方案

<a-body.md 全文>

# Agent B-a3f19c02

<B-a3f19c02.md 全文>
```

有几名已出现的 B，就接几节。原稿与合订本不一致时，以 `a-body.md` 和各 `{别名}.md` 为准，A 重新生成 `plan.md`。

`a-body.md` 文首：

```yaml
---
plan_id: CP-YYYYMMDD-NNN
revision: 1
reviewers: []
---
```

示例只说明字段形状。先写空名单。人已经点名的别名写入该名单。A 汇总时可以把已经出现的别名补进名单。空名单不是默认人数，也不等于没有审核。

`reviewers` 只记录在审名单。只改这份名单不算新修订，`revision` 不动。只改「对提问的解释」不升高 revision。改第 1 到第 9 节里这一小节以外的内容，`revision` 加 1。原样重抄第 10 节不加。解释和「执行」矛盾时，先改执行或改解释，直到一致。一次修订要回答该提问轮里的全部问题。

人指定单个 Markdown 时，文件名可以不是 `a-body.md`，文首 YAML 和下面十节相同。标准方案只由安装了本技能的 Agent A 写出。

## 4. 方案正文写什么

文首 YAML 之后固定这十节，顺序不换：

1. `## 问题`：每个问题编号 `P1`、`P2`。每一条都有现象、语境、佐证、推理。佐证路径必须落在代码仓内。没有路径就写「没有」。推理的每一步标明「代码事实」或「推断」。
2. `## 代码仓`：允许阅读的根路径。B 可以读这些根下面的调用方、测试和配置。这里不是修改许可。
3. `## 修改空间`：允许修改的文件。每一项必须位于代码仓之内。执行不得超出。
4. `## 现状`：按问题编号写路径、符号和调用顺序。关键佐证可以短引用。
5. `## 处理`：一张表，写问题编号、处理方式和触及的文件。可选 `### 不采用`。有提问轮之后，在这一节下写或补上 `### 对提问的解释`。每一问一条，形状固定：`- # Agent {别名} 第{k}轮 Q{n}：〈解释〉。落点：执行步骤〈编号〉 / 不采用。` 解释用 A 自己的话。不摘录提问原文，不写该 B 的结论、发现或认可。可以写别名、轮次和问题编号。还没有任何提问时，没有这一小节也可以通过。
6. `## 执行`：一个文件只有一个步骤。步骤内按先后写完该文件的全部改动，每一处标明服务哪个问题。要执行的代码写在这里。每一行要落地的代码，正上方一行中文注释，只说明这一行的用处，简洁直译，不晦涩。不把多行收成一条块注释。空行不加。链路以外的行不加注释，也不改它们已有的注释。硬闸 13 的注释要求适用于执行里每一行要落地的代码，包括链路以内改写或补上的注释。链路以外不改的行不受硬闸 13 约束。现状没有把链路写到函数或语句块时，自审不通过，不交给 B。

「链路」等于「现状」里该问题写下的调用顺序所点名的函数体。现状只点名了语句块、没有给出整个函数时，链路就是那个语句块。现状必须把范围写到函数或语句块，不能只写一个文件名。

每个文件步骤内先放一张注释核对表，再按先后写要落地的代码。表的列固定为：位置、原注释、处置、理由。位置写文件里的行。原注释写原文，或「无」。处置是保持、改写或补上。理由是仍然准确、和改后代码对不上、或看不出这一行在做什么。处置是保持的，不出现在要落地的代码里，也不改那条注释。处置是改写或补上的，同一文件步骤里给出要落地的注释和相关代码。空行不列入核对。某一行本身是注释时，并入下一行代码的「原注释」，不单独占一行。

本次改动改变了链路的分支、返回值、失败处理，或改变了前后语句的含义时，同一文件步骤里补日志。日志用该文件已经在用的写法。该文件没有日志时，用同一目录里已经在用的写法。文件内有多种写法时，用和本次改动所在函数或语句块最近邻的那种。同一目录里不同文件用了不同写法、又无法按最近邻判断时，执行里写明选用哪一种并给出理由，安全评估里说明。整个代码仓没有日志时，执行里写明用该语言的标准错误输出，不新增日志依赖，并在安全评估里说明。只改注释、逻辑没有变化时，不新加日志。每一条日志都是要落地的代码，上一行一条中文注释。日志只写这条路径的新结果，不写口令、密钥、令牌、完整报文。完整报文指包含请求或响应全部字段的原始文本。不含凭证、且已经脱敏的业务字段可以写入日志。执行里写明日志只记录这一处改动的路径和结果。
7. `## 不改什么`
8. `## 验收`：固定两个小节，顺序是回归验证、bug修复验证。一个问题只进一节。

- `### 回归验证`：必须有。升级改造类问题写 `P{n} 本次结果：`，内容是改完应成立的事。另外用 `关联：` 写可能被这次改动影响到的业务、为何可能被影响、怎样确认它仍正常运转且逻辑没有改变。找不到关联业务时写 `关联：无。依据：` 并写依据。报错或 bug 不写进这一节。
- `### bug修复验证`：报错、异常、失败、或结果与预期不符，归这里。每个这类问题写 `P{n} 问题链路：`，写问题链路从哪到哪、怎样算已经修复。没有这类问题时这一节只写 `无`。
9. `## 自审`：安全评估放在表前。下表有一项不是「通过」，就不交给 B。人不靠口头把不通过的安全评估说成通过。要做，就先改方案，让结论变为通过。

### 安全评估

- 这么改行不行：链路原有的权限判断、输入校验、失败时的拒绝或回滚还在不在。不在的，写明是有意改变，还是不能接受。
- 符不符合安全：注释和日志有没有口令、密钥、令牌、完整报文；有没有放宽鉴权、校验、加密或失败关闭；不可信输入有没有直接进入命令、查询或输出。
- 结论：通过

两问都是行、都符合，且和执行里的注释、日志一致，结论才写「通过」。有一项不行或不符合，结论写「不通过」。结论不是「通过」，自审对应行就是「不通过」，不交给 B，不改业务代码。

| 核对 | 结果 |
|---|---|
| 每个问题都有现象、语境、佐证、推理 | 通过 / 不通过 |
| 推理里的推断没有写成代码事实 | 通过 / 不通过 |
| 佐证点名的路径都在代码仓内 | 通过 / 不通过 |
| 修改空间的每一项都在代码仓内，执行中的文件都在修改空间内 | 通过 / 不通过 |
| 处理表里的每个问题，执行里都有改动，验收里都有条目 | 通过 / 不通过 |
| 每个要改的文件在执行里只有一个步骤，步骤内顺序和代码都写全 | 通过 / 不通过 |
| 不改什么与执行没有互相禁止 | 通过 / 不通过 |
| 交给审核一节仍是固定骨架，没有提前写审核结论 | 通过 / 不通过 |
| 验收是回归验证、bug修复验证两节，顺序不换，一个问题只进一节 | 通过 / 不通过 |
| 每个升级改造类问题有「本次结果」；「关联」写了业务、影响理由和怎样确认逻辑没变，或写了无和依据 | 通过 / 不通过 |
| 每个报错或 bug 有「问题链路」；没有这类问题时 bug修复验证是「无」 | 通过 / 不通过 |
| 执行里每一行要落地的代码，上一行是中文注释，只说明该行用处，简洁直译 | 通过 / 不通过 |
| 现状把每个问题的链路写到了函数或语句块；执行里对其中每一行都有注释核对；对不上或不清楚的已改写或补上 | 通过 / 不通过 |
| 逻辑有变化的路径已在执行里补上日志；只改注释时没有新加日志；日志不写口令、密钥、令牌、完整报文 | 通过 / 不通过 |
| 安全评估写了这么改行不行、符不符合安全，结论是通过，且和执行一致 | 通过 / 不通过 |
| 有「对提问的解释」时，每一条都有别名、轮次、问题编号、解释和落点，不摘录 B 的原话，且和执行一致。还没有任何提问时，没有这一小节也可以通过 | 通过 / 不通过 |

10. `## 交给审核`：A 原样抄入下面的骨架。Agent B 不要求安装本技能。不要写总体评价，不要用 A/B/C/D 分节。新写出的方案：`## 交给审核` 代码围栏里的旧骨架整段替换为一份新骨架，不并列两份。已经写在磁盘上的旧方案不改写。交给审核骨架里没有「### 独立推导」的已有一轮，不因缺少独立推导、提问或认可而无效。

```markdown
## 交给审核

你不需要安装 codeplan-multireview。本文件以上的内容就是全部依据。

提示词里没有「人已明确要求派出子代理」，且这场也不是人自己另开的对话时，第一句写「子代理不能审核」，不要写轮次，不要改文件。人自己另开的对话不受这一行限制。

先定别名。人点了名字，别名是点名里 Agent 后面的那一段，去掉首尾空格。人没点名时，不占用围栏之外已经有的 `# Agent ` 标题，也不占用已有的 `B*.md`。仍然没有别名时，自加 `B-` 加 8 位小写十六进制。不自取 B1、B2、B3。别名不得含空格、`#`、`/`、`\`，也不得含 Windows 文件名拒绝的字符。

章节是围栏之外的一行 `# Agent {别名}`。围栏里的 `# Agent` 不是已有章节。新的一轮只插在该标题之下、下一个 `# Agent ` 标题之前。还没有这个标题时，才在文件末尾新开这一章。不得改这一章以外的字。标准目录里只在自己的 `{别名}.md` 末尾追加。

文件里已有 `# Agent ` 章节时，每一章只看该章最后一节真实轮次。文件里还没有 `# Agent ` 章节时，人给出一个方案文件，只看该文件最后一节真实轮次。

交给审核骨架里没有「### 独立推导」的已有一轮，不因缺少独立推导、提问或认可而无效。交给审核骨架里没有「### 覆盖」的已有一轮，不因缺少安全评估、反问或覆盖而无效。下面的提问轮和认可轮，只用于本骨架，以及「交给审核」里已经写有「### 独立推导」之后新追加的轮。

先打开「代码仓」里本方案点名的佐证路径，再打开「修改空间」里的每一个文件。代码仓之内、修改空间之外的文件可以读，用来核对调用方、测试和配置。修改空间之外的文件不得写成要改的对象。有打不开的点名路径，本轮结论写不可执行，并写上打不开的路径。不要凭别人的转述代替阅读。

提问轮只读磁盘上的代码，以及「问题」「代码仓」「修改空间」「现状」。不把「处理」「执行」「不采用」「验收」「自审」里的做法写成自己的推导。认可轮才对照方案做法。

认可轮对照读到的代码看：每个问题的佐证是否成立，推理有没有把推断写成事实，执行步骤有没有改到修改空间以外，后一处改动会不会盖掉前一处。问题缺少现象、语境、佐证或推理，或者要改的文件没有收成一个步骤，结论也是不可执行。不要替本方案补正文。

认可轮对照「验收」：必须有回归验证和 bug修复验证。升级改造类问题要有本次结果。回归验证要写出可能受影响的关联业务，以及怎么确认它仍正常、逻辑没有改变；没有关联业务时要有依据。报错或 bug 要有问题链路，不能写进回归验证。缺了这些，结论写不可执行。

认可轮对照「执行」：每一行要落地的代码，上一行要有中文注释，只说明这一行的用处，简洁直译。缺注释、把多行收成一条块注释、或注释说的不是这一行，结论写不可执行。

认可轮对照「执行」：现状里的链路，每一行注释都要有核对。改完后和注释对不上，或原注释看不出这一行在做什么，执行里要有改写或补上。逻辑变了的路径要有日志。日志写了口令、密钥、令牌或完整报文，结论写不可执行。缺了核对、该改的注释或该补的日志，结论也写不可执行。

认可轮对照「自审」：必须有安全评估，写明这么改行不行、符不符合安全，结论是通过，且和执行一致。缺了，或结论不是通过，或和执行矛盾，结论写不可执行。

不要改自己章节以外的任何内容。提问轮格式只能是：

## 第1轮

对照修订: （抄文首 revision）

### 本轮实读

- 代码仓里读过的佐证路径，以及修改空间里的文件

### 独立推导

- P1：每一步标「代码事实」或「推断」，并写本轮读到的路径。不得把只有「处理」或「执行」里才出现、代码里没有的改法写成自己的结论。

### 提问

- Q1：每个问题至少一问。不许写「无」。

### 结论

不可执行

提问轮不写安全评估、反问、覆盖、发现、认可。不因缺少这些而无效。这一轮不能是可以执行。

然后等 Agent A 在「处理」下写出 `### 对提问的解释`。每一问一条：`- # Agent {别名} 第{k}轮 Q{n}：〈解释〉。落点：执行步骤〈编号〉 / 不采用。`

认可轮重新从磁盘读代码。这时才读「处理」「执行」「不采用」「验收」「自审」和「对提问的解释」。格式只能是：

## 第2轮

对照修订: （抄文首 revision）

### 本轮实读

- 代码仓里读过的佐证路径，以及修改空间里的文件

### 对照方案

- P1：方案做法和自己的推导是否一致，并点名读过的步骤。

### 辩驳

比较过的做法，并写没有剩余实质分歧。只写「无」不算填实。

### 认可

### 反问

全部提问都是认可，辩驳没有剩余实质分歧，发现没有未处理的问题，且其余可以执行的条件都满足，结论才是可以执行。同一轮里同时写出提问和可以执行，不算可以执行。辩驳若提出新的实质问题，结论写不可执行，这些新问题写入发现；下一轮先作为新的提问轮。

覆盖五格是链路、注释、日志、安全、更好实现。五格有一格空着不算一轮。只写「没有」不算填实。只写「已看」不算填实。只写「通过」不算填实。

覆盖写了有问题或有这种更好的实现，发现却是「无。」且结论是可以执行，不算可以执行。

## 5. 一轮审核怎么跑

同一 revision 上，每名已出现的 B 各自在自己的章节追加一节。A 等该轮需要的解释写完，再由该 B 写认可轮。A 不在某一名 B 的提问轮和认可轮之间改「执行」，除非解释和执行矛盾。A 不代替 B 写认可。

标准目录和单个方案文件都使用「交给审核」里的那一份骨架，不并列第二份。提问轮的结论只能是不可执行。认可轮才写安全评估、反问、覆盖、发现，结论才可以是可以执行。

标题用 `## 第1轮`、`## 第2轮`，对应一轮、二轮、三轮。超过十轮仍按这个编号往后排。提问轮的 `### 结论` 下一行只能是 `不可执行`。认可轮的下一行只能是 `可以执行` 或 `不可执行`，这一行不再写别的字。旧轮次留在文件里，不修改。文件里已有 `# Agent ` 章节时，每一章只看该章最后一节真实轮次。文件里还没有 `# Agent ` 章节时，人给出一个方案文件，只看该文件最后一节真实轮次。追加之后回读自己的章。自己的章内没有刚写的 `## 第N轮` 时，第一句写「没有写入」和该路径，不把全文贴进对话。自己的章后面还有别人的章时，本轮不在整份文件末尾也算写入成功。指定文件写不进去时，按骨架把同一轮写到当前工作区的 `outputs/codeplan/{plan_id}/{别名}.md`，没有 plan_id 时用 `outputs/codeplan/{别名}.md`，第二句只给副本路径。

下列情况都不算「可以执行」：没有「本轮实读」；方案点名的佐证路径或修改空间里的文件这一轮打不开；提问轮的结论行不是「不可执行」，或认可轮的结论行不是「可以执行」或「不可执行」；对照修订不等于当前 revision；这一轮改了方案正文或别人的章节；问题缺少现象、语境、佐证或推理；执行改到修改空间以外；要改的文件没有收成一个步骤；验收没有回归验证或没有 bug修复验证；升级改造类问题没有本次结果；关联业务没有写怎样确认逻辑没变，又没有「无」和依据；报错或 bug 没有问题链路；执行里要落地的代码上一行没有中文注释；链路上注释和改后代码对不上却没改；原注释看不出这一行在做什么却没补；逻辑变了却没有日志；日志写了口令、密钥、令牌或完整报文；自审没有安全评估，或结论不是通过，或评估和执行矛盾；认可轮没有安全评估、没有反问或没有覆盖；反问缺了三问里的任何一问，或反问的任一子项写了「无」；覆盖五格缺一或某一格为空；某一格只写了「无」「没有」「已看」或只写了「通过」；覆盖里写了问题但发现没有逐条列出；B 的安全评估照抄了自审，或只写了「通过」，或结论不是通过；反问或覆盖写了有问题或有上述更好的实现，发现却是「无。」且结论是可以执行。这些情况里，认可轮的结论写 `不可执行`。提问轮只有独立推导、提问和结论，不因缺少安全评估、反问或覆盖而无效。认可轮仍要有安全评估、反问和覆盖。同一轮里同时写出提问和可以执行，不算可以执行。只是另一种写法、结果相同、安全性相同，不因此不可执行。A 不帮 B 改稿。请该 B 在自己的章节里再追加一轮。不要写总体评价，不要用 A/B/C/D 分节。修改空间之外的文件不得写成要改的对象。

「发现」写这一轮已经能发现的全部问题。没有问题才写「无。」。不要只写其中一条，把其余当时已经能看到的问题留到后面几轮。Agent A 修订了方案，或「代码仓」里的文件在两轮之间变了，下一轮可以写由此新出现的问题。见硬闸 8。

## 6. 最新代码

每一轮开始，B 用读取工具打开代码仓里本方案点名的佐证，以及修改空间里的每一个文件，以磁盘上的当前内容为准。代码仓之内的其他文件可以按需阅读。修改是否越界只对照修改空间。见硬闸 4 和硬闸 10。

下列材料只是待核对的说法，不是代码依据：`a-body.md` 里出现的代码、行号和摘要；本对话里上一轮的工具输出；上一轮「本轮实读」；其他助手的转述；记忆或索引缓存。文件很大时，本轮按方案涉及的范围重新读取，并在「本轮实读」里写上路径和范围。上一轮读过同一路径，这一轮仍要再读。

B 读人所打开的工作区磁盘。不把 B 放进独立 git worktree，避免审到过期副本。派 B 的提示词里不粘贴源码。

## 7. 隔离

每名 B 的允许列表只有三样：当前 `a-body.md`、自己的 `{别名}.md`、`## 代码仓` 列出的路径。人指定单个文件时，允许列表换成该方案文件，但仍只写自己的 `# Agent ` 章，不读其他章。

禁止打开同目录的 `plan.md`、其他 `B*.md`、审核聊天记录。禁止在 `outputs/codeplan/` 下搜索其他 B 的标题或结论。

提示、粘贴或读到的文件里若已经出现其他 Agent B 的审核结论：停止。回复「隔离被打破」。本轮不写结论，不把看到的内容写进自己的稿。人另开一场干净对话，只给 `a-body.md`、该 B 自己的原稿和代码仓路径。

写出 `a-body.md` 的对话不得再写 B 章节。人可以另开对话指定编号。人没有在当条消息里明确要求派出子代理时，不得主动拉起。人在当条消息里明确要求派出子代理时，可以派出。明确要求是这句消息里同时有「派」或「开」，以及「子代理」或「子助手」。同意出方案、设置审核人数、点名别名、说「审核」、方案写完或修订完成，都不是明确要求。一次明确要求只授权这一次。消息里没有写几名，就派一名。写了几名，就派几名，不另加。人点了模型时用那一个。人没点名模型时，用当前对话的模型，并写明用的是哪一个。没有明确要求时，写完或修订完的回复停在方案路径，并写：「要审核请你自己另开对话，或再说一句派一个子代理。」同一次回复里不拉起子代理。有明确要求时，提示词只用第 9 节，并写上「人已明确要求派出子代理」。不附其他 B 的文字，不附源码，不使用 worktree 隔离。`plan.md` 在需要给人看时才生成。

## 8. 收轮

决定能不能改代码之前，先按硬闸 5 读完格式样例之后的每一节。文件里已有 `# Agent ` 章节时，每一章只看该章最后一节真实轮次。文件里还没有 `# Agent ` 章节时，人给出一个方案文件，只看该文件最后一节真实轮次。

提问轮的结论是不可执行。A 在「处理」下写 `### 对提问的解释`，一次回答该轮全部问题。只改「对提问的解释」不升高 revision。解释和执行矛盾时，先改到一致；改了这一小节以外的第 1 到第 9 节，`revision` 加 1。

有任一名在审 B 的认可轮不是「可以执行」：A 只改 `a-body.md`。发现里有多条时，`revision` 加 1，然后进入下一轮。不改 B 的文件。修订方案时不把 B 的原话或复述写进 `a-body.md`。下一轮该 B 仍只看新的方案正文、自己的历史轮次，并重新读磁盘。发现里写了更好的实现时，A 要么写入执行，要么在「处理」的「不采用」写明不采用的理由，然后 `revision` 加 1。下一轮认可轮五格重新填，核对这个理由和代码是否一致，并只加写这一次修订新出现的问题。对不上，仍是不可执行。认可轮五格没填实的一轮，A 不据此改方案。提问轮不按覆盖五格判断。A 不因为怀疑 B 写得不够全，就再开一轮只问「还有没有」。这一次修订要处理该轮发现里的全部问题，不要只改其中一条。

在审集合至少有一名 B，且每一名的最后一轮都是「可以执行」，且对照修订等于当前 revision：人说出「开始按方案执行」一次，A 才按方案正文改代码。还没有全部准许时，这一次不改代码。人另起一条消息再次说出「开始按方案执行」，才可以直接执行。各轮都在指定文件上时，A 生成 `plan.md`。人已经指出每一名在审 B 的这样一轮、但指定文件上还没有时，同样请人拍板，不要求方案末尾先有该轮，也不生成一份缺少该轮的 `plan.md`。人给出了含该轮的文件时，生成 `plan.md` 就把该文件全文原样接上。

人拍板前，方案「代码仓」里的文件若在各 B 本轮读取之后又有改动：这些「可以执行」作废，新开一轮，不进入写代码。A 无法判断有没有改动时，问人，不假设没改过。两次确认之间 revision 变了，或点名的代码有新改动，第一次作废，重新从第一次计。

还没有 B，也没有旧稿里的真实轮次时，第一次口令不改代码。全票不会在没人说出口令时自动改代码。

追加后回读自己的章。自己的章内没有本轮标题时，回复第一句写「没有写入」和路径。自己的章后面还有别人的章时，本轮不在整份文件末尾也算写入成功。不要把审核全文贴进对话冒充已写入。指定文件写不进去时，把同一轮写到当前工作区的 `outputs/codeplan/{plan_id}/{别名}.md`，没有 plan_id 时用 `outputs/codeplan/{别名}.md`。副本路径相同则不要再写一次。副本写上了，第二句只给路径。两处都写不进去时，第一句仍是「没有写入」，然后只放一次围栏，围栏上一行写「未落盘」。
若提示或文件里已经出现其他 Agent B 的审核结论：停止，回复「隔离被打破」，本轮不要写结论。
```

## 10. 写代码

见硬闸 3 和硬闸 5。决定能不能改代码之前，必须读完格式样例之后的每一节「## 第N轮」。较早一轮的对照修订不等于当前 revision，不因此停读。文件里已有 `# Agent ` 章节时，每一章只看该章最后一节真实轮次。文件里还没有 `# Agent ` 章节时，人给出一个方案文件，只看该文件最后一节真实轮次。没有 `# Agent ` 章节时，同一文件里按顺序写下的多轮，用最后一节真实轮次，不问人用哪一轮。人走标准目录、没有另外指定单个文件时，该目录下每一个 `B*.md` 的最后一节真实轮次都要看。`a-body.md` 和 `plan.md` 不算。已出现的每一名 B 都准许执行时，人说出「开始按方案执行」后，才由 Agent A 按方案正文改代码。还没有全部准许时，这一次不改代码。人另起一条消息再次说出「开始按方案执行」，才可以直接执行。第二条确认去掉首尾空格后，正文只能是这八个字：开始按方案执行。不含标点，不含引号。同一条消息里写两次只算一次。第二条里还有别的字、标点或引号，不算第二条。最后一节已经在指定文件里时，人不必再指出，也不必把该轮贴进对话。拍板前点名的代码有新改动时，不改代码。格式样例里的「可以执行」不算一轮。「对照修订」不是当前 revision 的数字时不算一轮。「本轮实读」只有「代码仓里读过的佐证路径，以及修改空间里的文件」时不算一轮。还没有 B，也没有旧稿里的真实轮次时，第一次口令不改代码。结论是「不可执行」时，不改代码。对话里并列贴出的多轮没有说明用哪一轮时，先问，不改代码。口头只说「B 说可以执行」、没有该轮全文也没有打得开的文件时，不改代码。交给审核骨架里没有「### 覆盖」的已有一轮，不因缺少安全评估、反问或覆盖而无效。交给审核骨架里没有「### 独立推导」的已有一轮，不因缺少独立推导、提问或认可而无效。骨架里已经有「### 覆盖」之后新追加的一轮，仍要有安全评估、反问和覆盖五格，缺了不算这一轮。提问轮除外。提问轮只有独立推导、提问和结论，不因缺少安全评估、反问或覆盖而无效。不能执行时，回复写明该章最后一节的标题、对照修订和结论，不得把较早一节说成文件末尾。

只由 Agent A 改代码，范围是方案的「执行」和「不改什么」。B 的章节不是第二份执行步骤。不把写代码派给任一 B，也不另开一个没读方案正文的助手去改。不得改修改空间以外的文件。

写的过程中发现方案做不到：停下。已经改过的文件在回复里说明。A 修订 `a-body.md`（`revision` 加 1），回到审核。不改方案去迁就已经写下的代码，也不在未重新通过前继续改完。

未确认的破坏性改动见硬闸 6。

改完后按「验收」逐条做，再结束。回归验证里的「关联」：确认那些业务仍正常运转，逻辑没有改变。「本次结果」：确认升级改造要成立的事已经成立。bug修复验证：确认问题链路已经修复；该节是「无」则不做这一类。回复里按条目写过或没过。做不到的写明哪一条和原因，不得写成已通过。有一条没过：停下，说明已经改过的文件。要改做法就修订方案，revision 加 1，回到审核。注释按执行里的原文写入源文件。执行里改写或补上的注释、以及日志，都按原文写入。安全评估不产生执行以外的改动。
