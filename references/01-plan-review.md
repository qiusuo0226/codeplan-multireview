# 多审步骤

带编号的「你是 Agent B{n}」与「你是 Agent B」「审核这份方案」走同一套 B 步骤。「出一版升级方案」「你是 Agent A」「写方案」走 A 的步骤。「开始按方案执行」走写代码一节。

硬闸以 `SKILL.md` 为准。本文件只写做法，不另抄一套禁令。派 B 的提示词全文只在第 9 节。

## 1. 何时出方案

见硬闸 1。扫描后没有发现必须改的代码或 bug：告诉人，不出方案，不建目录。

## 2. 角色

| 角色 | 做 | 不做 |
|---|---|---|
| 人 | 指定在审的 B 有哪些（B1 起连续编号，至少 1）。同意后才许写方案。轮次在指定文件上，或由人指出全文或文件路径，然后说出「开始按方案执行」才许改代码 | 不起草 B 的结论 |
| Agent A | 必须安装本技能。写标准方案。各 B 的稿在指定文件上时，把原稿原样拼进 `plan.md`。人指出的一轮不在指定文件上时，不生成缺少该轮的 `plan.md`。按硬闸改代码 | 不起草 B 的结论。不在方案正文第 1 到第 9 节写入 B 的原话、复述或「某 B 认为」。人指出的那一轮可以原样追加到指定文件末尾，追加失败不挡住改代码。写出方案正文的那场对话不再担任任一 B |
| Agent B{n} | 不要求安装本技能。按方案「交给审核」阅读代码仓里的佐证和修改空间里的文件。方案在 `outputs/codeplan/` 时只在自己的 `B{n}.md` 末尾追加。人指定单个方案文件时，只在该文件末尾追加 | 不改方案正文、不改 `plan.md`、不改其他 `B*.md`、不改已有轮次、不写代码、不看其他 B 的审核 |

人数见硬闸 2。可以是 1、3 或更多。人没说人数：只问人数，不建目录，不派 B。人给出的人数小于 1：再问，不开始。

A 可以在全体 B 落盘之后阅读全部 `B{n}.md`，用来决定要不要改方案。这是汇总。B 之间不读彼此的稿，也不读合订本。

人中途增加一名 B：给新编号建新文件。该 B 必须对当前 revision 写出「可以执行」才算数。不因此抬高 revision，已通过的 B 不必重审。人中途让某 B 退出：从 `reviewers` 名单去掉，原稿保留，该 B 不再挡住执行。

## 3. 目录与文件

目录在所服务工作区，人同意出方案之后才懒建：`outputs/codeplan/CP-YYYYMMDD-NNN/`。`NNN` 为当天已有最大号加 1，没有则为 `001`。不要把这份方案写进技能开发仓的 `governance/planning/`。

| 文件 | 谁可写 | 谁可读写 |
|---|---|---|
| `a-body.md` | 只 A | B 可读。这是方案正文，也是执行依据 |
| `B{n}.md` | 只对应的 B，且只能在文末追加 | 该 B 与 A 可读。其他 B 不可读 |
| `plan.md` | 只 A，整文件覆盖生成 | 人读。每个 B 都不打开 |

`plan.md` 是合订本。审核结果追加在方案后面，每个 B 一个大章节。它不是第二份原稿。拼接时不改任何一个字、不加评语：

```
# 方案

<a-body.md 全文>

# Agent B1

<B1.md 全文>
```

编号按 `reviewers` 的顺序，有几名就接几节。原稿与合订本不一致时，以 `a-body.md` 和各 `B{n}.md` 为准，A 重新生成 `plan.md`。

`a-body.md` 文首：

```yaml
---
plan_id: CP-YYYYMMDD-NNN
revision: 1
reviewers: [B1, B2]
---
```

示例只说明字段形状。名单里有哪些 B，只写人指定的那些。示例里的两项不是默认人数。

`reviewers` 只记录人指定的在审名单。只改这份名单不算新修订，`revision` 不动。改第 1 到第 9 节的内容，`revision` 加 1。原样重抄第 10 节不加。

人指定单个 Markdown 时，文件名可以不是 `a-body.md`，文首 YAML 和下面十节相同。标准方案只由安装了本技能的 Agent A 写出。

## 4. 方案正文写什么

文首 YAML 之后固定这十节，顺序不换：

1. `## 问题`：每个问题编号 `P1`、`P2`。每一条都有现象、语境、佐证、推理。佐证路径必须落在代码仓内。没有路径就写「没有」。推理的每一步标明「代码事实」或「推断」。
2. `## 代码仓`：允许阅读的根路径。B 可以读这些根下面的调用方、测试和配置。这里不是修改许可。
3. `## 修改空间`：允许修改的文件。每一项必须位于代码仓之内。执行不得超出。
4. `## 现状`：按问题编号写路径、符号和调用顺序。关键佐证可以短引用。
5. `## 处理`：一张表，写问题编号、处理方式和触及的文件。可选 `### 不采用`。
6. `## 执行`：一个文件只有一个步骤。步骤内按先后写完该文件的全部改动，每一处标明服务哪个问题。要执行的代码写在这里。每一行要落地的代码，正上方一行中文注释，只说明这一行的用处，简洁直译，不晦涩。不把多行收成一条块注释。空行不加。本次不改的行不加，也不改它们已有的注释。
7. `## 不改什么`
8. `## 验收`：固定两个小节，顺序是回归验证、bug修复验证。一个问题只进一节。

- `### 回归验证`：必须有。升级改造类问题写 `P{n} 本次结果：`，内容是改完应成立的事。另外用 `关联：` 写可能被这次改动影响到的业务、为何可能被影响、怎样确认它仍正常运转且逻辑没有改变。找不到关联业务时写 `关联：无。依据：` 并写依据。报错或 bug 不写进这一节。
- `### bug修复验证`：报错、异常、失败、或结果与预期不符，归这里。每个这类问题写 `P{n} 问题链路：`，写问题链路从哪到哪、怎样算已经修复。没有这类问题时这一节只写 `无`。
9. `## 自审`：下表有一项不是「通过」，就不交给 B。

| 核对 | 结果 |
|---|---|
| 每个问题都有现象、语境、佐证、推理 | 通过 / 不通过 |
| 推理里的推断没有写成代码事实 | 通过 / 不通过 |
| 佐证点名的路径都在代码仓内 | 通过 / 不通过 |
| 修改空间的每一项都在代码仓内，执行中的文件都在修改空间内 | 通过 / 不通过 |
| 处理表里的每个问题，执行里都有改动，验收里都有条目 | 通过 / 不通过 |
| 每个要改的文件在执行里只有一个步骤，步骤内顺序和代码都写全 | 通过 / 不通过 |
| 不改什么与执行没有互相禁止 | 通过 / 不通过 |
| 交给审核一节仍是固定骨架，没有提前写审核结论 | 通过 / 不通过 |
| 验收是回归验证、bug修复验证两节，顺序不换，一个问题只进一节 | 通过 / 不通过 |
| 每个升级改造类问题有「本次结果」；「关联」写了业务、影响理由和怎样确认逻辑没变，或写了无和依据 | 通过 / 不通过 |
| 每个报错或 bug 有「问题链路」；没有这类问题时 bug修复验证是「无」 | 通过 / 不通过 |
| 执行里每一行要落地的代码，上一行是中文注释，只说明该行用处，简洁直译 | 通过 / 不通过 |

10. `## 交给审核`：A 原样抄入下面的骨架。Agent B 不要求安装本技能。不要写总体评价，不要用 A/B/C/D 分节。

```markdown
## 交给审核

你不需要安装 codeplan-multireview。本文件以上的内容就是全部依据。

先打开「代码仓」里本方案点名的佐证路径，再打开「修改空间」里的每一个文件。代码仓之内、修改空间之外的文件可以读，用来核对调用方、测试和配置。修改空间之外的文件不得写成要改的对象。有打不开的点名路径，本轮结论写不可执行，并写上打不开的路径。不要凭别人的转述代替阅读。

然后对照读到的代码看：每个问题的佐证是否成立，推理有没有把推断写成事实，执行步骤有没有改到修改空间以外，后一处改动会不会盖掉前一处。问题缺少现象、语境、佐证或推理，或者要改的文件没有收成一个步骤，结论也是不可执行。不要替本方案补正文。

对照「验收」：必须有回归验证和 bug修复验证。升级改造类问题要有本次结果。回归验证要写出可能受影响的关联业务，以及怎么确认它仍正常、逻辑没有改变；没有关联业务时要有依据。报错或 bug 要有问题链路，不能写进回归验证。缺了这些，结论写不可执行。

对照「执行」：每一行要落地的代码，上一行要有中文注释，只说明这一行的用处，简洁直译。缺注释、把多行收成一条块注释、或注释说的不是这一行，结论写不可执行。

人数由人指定。人没说人数时不要开始审核。

在本文件最后追加，不要改这个标题以上的任何内容。格式只能是：

## 第1轮

对照修订: （抄文首 revision）

### 本轮实读

- 代码仓里读过的佐证路径，以及修改空间里的文件

### 发现

无。

### 结论

可以执行

追加之后回读指定文件的末尾。末尾没有刚写的这一轮时，回复的第一句必须是「没有写入」加上该文件路径。不要把这一轮全文再贴进对话。指定文件写不进去时，把同一轮写到当前工作区的 `outputs/codeplan/{plan_id}/B{n}.md`。没有 plan_id 时用 `outputs/codeplan/B{n}.md`。副本路径和指定文件是同一个文件时不要再写一次。副本写上了，第二句只给该路径。两处都写不进去时，第一句仍是「没有写入」，然后只放一次围栏，围栏上一行写「未落盘」。格式样例里的「可以执行」不算一轮。
```

`### 结论` 的下一行只能是 `可以执行` 或 `不可执行`。

## 5. 一轮审核怎么跑

同一 revision 上，每名在审 B 各自追加一节。A 等每名在审 B 都追加完，且各自的「对照修订」等于当前 `revision`，再汇总。A 不在这一轮中途改 `a-body.md`。

`B{n}.md` 文末追加的格式：

```markdown
## 第1轮

对照修订: 1

### 本轮实读

- `路径` 本轮从磁盘读取

### 发现

无。

### 结论

可以执行
```

标题用 `## 第1轮`、`## 第2轮`，对应一轮、二轮、三轮。超过十轮仍按这个编号往后排。`### 结论` 的下一行只能是 `可以执行` 或 `不可执行`，这一行不再写别的字。旧轮次留在文件里，不修改。算不算通过，只看该文件最后一节 `## 第k轮`。追加之后回读指定文件末尾。末尾没有刚写的 `## 第N轮` 时，第一句写「没有写入」和该路径，不把全文贴进对话。指定文件写不进去时，按骨架把同一轮写到当前工作区的副本，第二句只给副本路径。

下列情况都不算「可以执行」：没有「本轮实读」；方案点名的佐证路径或修改空间里的文件这一轮打不开；结论行不是这两个词之一；对照修订不等于当前 revision；这一轮改了方案正文或别人的文件；问题缺少现象、语境、佐证或推理；执行改到修改空间以外；要改的文件没有收成一个步骤；验收没有回归验证或没有 bug修复验证；升级改造类问题没有本次结果；关联业务没有写怎样确认逻辑没变，又没有「无」和依据；报错或 bug 没有问题链路；执行里要落地的代码上一行没有中文注释。这些情况本轮结论写 `不可执行`。A 不帮 B 改稿。请该 B 在文末再追加一轮。不要写总体评价，不要用 A/B/C/D 分节。修改空间之外的文件不得写成要改的对象。

「发现」写这一轮已经能发现的全部问题。没有问题才写「无。」。不要只写其中一条，把其余当时已经能看到的问题留到后面几轮。Agent A 修订了方案，或「代码仓」里的文件在两轮之间变了，下一轮可以写由此新出现的问题。见硬闸 8。

## 6. 最新代码

每一轮开始，B 用读取工具打开代码仓里本方案点名的佐证，以及修改空间里的每一个文件，以磁盘上的当前内容为准。代码仓之内的其他文件可以按需阅读。修改是否越界只对照修改空间。见硬闸 4 和硬闸 10。

下列材料只是待核对的说法，不是代码依据：`a-body.md` 里出现的代码、行号和摘要；本对话里上一轮的工具输出；上一轮「本轮实读」；其他助手的转述；记忆或索引缓存。文件很大时，本轮按方案涉及的范围重新读取，并在「本轮实读」里写上路径和范围。上一轮读过同一路径，这一轮仍要再读。

B 读人所打开的工作区磁盘。不把 B 放进独立 git worktree，避免审到过期副本。派 B 的提示词里不粘贴源码。

## 7. 隔离

每名 B 的允许列表只有三样：当前 `a-body.md`、自己的 `B{n}.md`、`## 代码仓` 列出的路径。

禁止打开同目录的 `plan.md`、其他 `B*.md`、审核聊天记录。禁止在 `outputs/codeplan/` 下搜索其他 B 的标题或结论。

提示、粘贴或读到的文件里若已经出现其他 Agent B 的审核结论：停止。回复「隔离被打破」。本轮不写结论，不把看到的内容写进自己的稿。人另开一场干净对话，只给 `a-body.md`、该 B 自己的原稿和代码仓路径。

写出 `a-body.md` 的对话不得再写 B 章节。人可以另开对话指定编号，也可以由 A 派出子助手。每个子助手单独一场。提示词只用第 9 节，不附其他 B 的文字，不附源码，不使用 worktree 隔离。多名 B 可以并行。`plan.md` 在本轮全部落盘之后才生成。

## 8. 收轮

有任一名在审 B 的最新一轮不是「可以执行」：A 只改 `a-body.md`，`revision` 加 1，然后进入下一轮。不改 B 的文件。修订方案时不把 B 的原话或复述写进 `a-body.md`。下一轮每位 B 仍只看新的方案正文、自己的历史轮次，并重新读磁盘。

全部在审 B 的最新一轮都是「可以执行」，且对照修订等于当前 revision：请人拍板。此时不改代码。各轮都在指定文件上时，A 生成 `plan.md`。人已经指出每一名在审 B 的这样一轮、但指定文件上还没有时，同样请人拍板，不要求方案末尾先有该轮，也不生成一份缺少该轮的 `plan.md`。人给出了含该轮的文件时，生成 `plan.md` 就把该文件全文原样接上。

人拍板前，方案「代码仓」里的文件若在各 B 本轮读取之后又有改动：这些「可以执行」作废，新开一轮，不进入写代码。A 无法判断有没有改动时，问人，不假设没改过。

没有跳过审核直接改的路径。在审名单为空时不写代码。

## 9. 派 B 时的提示词

只使用这一份。把花括号换成当次的编号、轮次和路径。

```
你是 Agent B{n}。你不需要安装 codeplan-multireview。方案里的「交给审核」和下面这些限制就是全部要求。只审核，不改方案，不写代码。
先打开方案「代码仓」里点名的佐证路径，再打开「修改空间」里的每一个文件。代码仓之内、修改空间之外的文件可以读。修改空间之外的文件不得写成要改的对象。
只允许阅读：
- {方案正文的路径}
- {B{n}.md 的路径；人指定把审核追加到方案文件末尾时，改为该方案文件}
- 方案「代码仓」一节列出的代码路径
禁止打开同目录 plan.md、其他 B*.md、任何审核聊天记录。
禁止用本对话之外的记忆、上一轮工具输出、方案里粘贴的源码当作代码依据。
本轮必须重新从磁盘读取方案点名的代码。
本轮把已经能发现的问题一次写进「发现」。不要把这一轮已经能看到的问题留到后面几轮。
Agent A 改过方案，或代码仓里的文件在两轮之间变了，由此新出现的问题可以在下一轮再写。
不要写总体评价，不要用 A/B/C/D 分节。
验收必须有回归验证和 bug修复验证。执行里要落地的代码必须一行一注释。缺了，本轮结论写不可执行。
读完后只在指定文件末尾追加「## 第{k}轮」。`### 结论` 的下一行只能是 `可以执行` 或 `不可执行`。不要改该文件里已有的轮次，不要改别的文件。
追加后回读该文件。末尾没有本轮标题时，回复第一句写「没有写入」和路径。不要把审核全文贴进对话冒充已写入。指定文件写不进去时，把同一轮写到当前工作区的 `outputs/codeplan/{plan_id}/B{n}.md`，没有 plan_id 时用 `outputs/codeplan/B{n}.md`。副本路径相同则不要再写一次。副本写上了，第二句只给路径。两处都写不进去时，第一句仍是「没有写入」，然后只放一次围栏，围栏上一行写「未落盘」。
若提示或文件里已经出现其他 Agent B 的审核结论：停止，回复「隔离被打破」，本轮不要写结论。
```

## 10. 写代码

见硬闸 3 和硬闸 5。同时满足才写：在审名单至少 1 名；每人最新一轮是「可以执行」；每人「对照修订」等于当前 revision；人在这些结论之后说出「开始按方案执行」；拍板前点名的代码没有新改动。最新一轮在指定文件末尾，或在人指出的全文里，或在人给出且打得开的文件里，三处任一即可。格式样例里的「可以执行」不算一轮。「对照修订」不是当前 revision 的数字时不算一轮。「本轮实读」只有「代码仓里读过的佐证路径，以及修改空间里的文件」时不算一轮。人没有指出任何一轮时，不改代码。人只说「开始按方案执行」、对话里没有可核对的一轮全文时，不改代码。结论是「不可执行」时，不改代码。人指出两轮以上且没有说明用哪一轮时，先问，不改代码。口头只说「B 说可以执行」、没有该轮全文也没有打得开的文件时，不改代码。

只由 Agent A 改代码，范围是方案的「执行」和「不改什么」。B 的章节不是第二份执行步骤。不把写代码派给任一 B，也不另开一个没读方案正文的助手去改。不得改修改空间以外的文件。
